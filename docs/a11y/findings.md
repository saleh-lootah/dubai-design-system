# Code Review Findings

Synthesis of `docs/a11y/baseline-2026-08-20.md` (automated tools) and
`docs/a11y/manual-review.md` (hand review) — both dated 2026-08-20, branch
`chore/codebase-review-harness`. This document adds no new investigation; every row
below traces to one or both source documents. Read those two first for full method and
raw evidence (`docs/a11y/raw-*.txt`).

Severity: **CRITICAL** breaks a user task or a component's core functionality entirely
(a total lockout or total non-function, not a partial degradation). **HIGH** fails WCAG
at level A or AA with the component still partially usable. **MEDIUM** is a fault a user
can work around, or a defect without a clean WCAG citation. **LOW** is a defect in
quality (lint, formatting, doc completeness, code smell) with no functional or
accessibility consequence.

The table is sorted CRITICAL → LOW. Three categories sit outside that ranking, in their
own sections at the end, because forcing them into CRITICAL–LOW would overstate or
understate what is actually known: **Open Items** (genuinely unresolved — need a live
browser/AT check, not a pass or fail from source alone) and **Informational** (confirmed
non-defects, kept for traceability, not queued for repair).

## A resolved disagreement between the two source documents, called out explicitly

The baseline's automated WCAG 2.1.1 (keyboard reachability) sweep reports **0**
failures project-wide. The manual review found **3 real, confirmed keyboard lockouts**
the automated number misses entirely: `dda-accordion` (F-001), `dda-avatar` (F-002),
`dda-chip` (F-003). This is not the automated tool being wrong about what it measured --
it is a structural blind spot, explained and cited at F-046: the checker's `INTERACTIVE`
selector only verifies that elements *already marked* interactive are reachable; a
`<div>`/`<span>` with an `onClick` and no `tabindex` was never a candidate in the first
place, so failing to reach it can't register as a shortfall. Both numbers are recorded
here -- 0 from the tool, 3 confirmed by source reading -- rather than one silently
overriding the other.

**Update (Task 12):** F-001/F-002/F-003 are now closed (see the table below) -- all
three headers/triggers are real `<button>` elements. The tool's structural blind spot
itself (F-046) is unchanged and still real: nothing was done to teach the checker to
see this class of defect, so a *future* instance of the same pattern would again read
as 0 failures. This section is kept for the history; do not read the 3 closures as
having fixed F-046.

## Informational -- confirmed non-defects, not queued for repair

- **I-001.** `dda-breadcrumb`'s `breadcrumbs` ghost attribute (1 of the 106 counted in
  F-042/baseline) is a known-benign false-positive-by-design:
  `dda-breadcrumb.stories.tsx` destructures `breadcrumbs` out of `args` and re-encodes it
  as a real `data-breadcrumbs` attribute (`const { breadcrumbs, ...otherArgs } = args`).
  The rendered markup works correctly. Counted in the 106 total because the checker's
  literal contract flags any `args` key without a matching `@Prop()` -- not because it's a
  real defect. **Do not rank for repair.**
- **I-002.** `dda-button.css`'s `.light-mode.btn-color-*` rule set (e.g. `:30-45,63-75,
  91-101,333-336,...`) is reachable, live code -- not dead code an earlier draft mistakenly
  flagged for removal. `component_mode="light-mode"` is a real, documented value
  (`dda-button.stories.tsx:58-62`; the same pattern recurs in ~28 components' stories). It
  fails with the exact same computed numbers as F-019/F-020 because it resolves to the
  same underlying color tokens in light theme -- not a separate defect, already covered by
  F-019/F-020 (both now closed, see above -- the `.light-mode` variants share the same
  fix).
- **I-003.** `dda-phonefield` and `dda-creditcard-field` do not block paste (grepped both
  for `paste`/`onPaste`/`preventDefault` -- no matches in either; both reformat on
  `onInput` without rejecting the action). Confirmed WCAG 3.3.8 compliant on this specific
  point. No action needed.
- **I-004.** `dda-range-slider` correctly implements native keyboard/ARIA slider
  semantics via two real `<input type="range">` elements (`dda-range-slider.tsx:64-76,
  78-92`) -- implicit `role="slider"` and `aria-valuenow/min/max` come from the browser
  automatically, and arrow keys work with no custom code. The one exception to this
  codebase's pattern of custom, under-implemented widgets (`dda-select`, `dda-dropdown`,
  `dda-tabs`). Its separate WCAG 2.5.8 target-size failure (F-022, now closed) was about
  hit-area size, not this keyboard/ARIA question.
- **I-005. New (Task 12).** `Components/Tabs TextTabs` and `Components/Tabs
  TextIconTabs` fail axe's `color-contrast` rule and are named explicitly among the
  current stable a11y-sweep failures remaining after F-023's colour-token fix took the
  sweep from 27 stable failures to 6 (Task 9j, re-measured before/after in the same
  environment). Independently recomputed by hand from the real cascade in
  `global/color.css`: 21.0:1 -- nowhere near a failure. `docs/a11y/contrast-decision.md` (F-023's decision record) explicitly
  scopes this out under "What is NOT decided here": *"Axe flags them; computation gives
  21.0:1. Unexplained from source. That is a question about the harness or the rendered

  stories when axe runs), not a design decision. Recorded as informational per that
  document's own conclusion, not as a queued colour-fault repair.

## Note on review depth

`dda-breadcrumb`, `dda-pagination`, and `dda-credit-card` received a lighter-touch check
than the other 31 components -- they had no dedicated question in the manual review's
brief for their group. They are **not cleared**; they are less examined than everything
else in this report. Their entries above (F-025 for breadcrumb, F-027 for both, O-003,
O-004, F-033, O-005 for credit-card) are real but should not be read as an exhaustive
audit of those three. **This still holds after the repair tasks**: none of the three
received a dedicated repair task, so the "less examined, not cleared" caveat applies
undiminished -- `dda-breadcrumb` and `dda-pagination` did each gain a test suite (Task 11
added `dda-breadcrumb`'s), but a test suite exercises the behaviour someone thought to
write a test for, not an independent re-audit of what a lighter-touch manual review may
have missed.
