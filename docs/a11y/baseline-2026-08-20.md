### Caveat: the axe numbers are provisional, not a stable invariant — in BOTH themes

This task ran the sweep **three times** against the same, unrebuilt `storybook-static`
build, in the same session, with a warm Storybook/Jest cache:

1. The brief's designated run, `npm run test:a11y:ci`, whose output is the committed
   `raw-a11y.txt`.
2. A bare `test-storybook --json` rerun immediately after, for machine-parseable
   per-story detail — committed as `raw-a11y-rerun1.txt`.
3. A second bare `test-storybook --json` rerun, to check whether run 2 was itself stable
   — committed as `raw-a11y-rerun2.txt`.

Runs 2 and 3 agreed with each other exactly (same 35 failing tests, same messages,
byte-identical failure sets). **Run 1 (the committed, brief-designated run) disagreed
with runs 2 and 3 — on the light-theme side, not just the already-known dark-theme
`Components/Header Default` flake:**

| | Run 1 (`raw-a11y.txt`, committed) | Runs 2 & 3 (`raw-a11y-rerun{1,2}.txt`, committed) |
| --- | --- | --- |
| Light instances / distinct stories | 14 / 14 | 16 / 16 |
| Dark instances / distinct stories | 28 / 25 | 29 / 25 |
| Union distinct stories | 29 | 29 |

**Light-theme finding, new to this task:** runs 2 and 3 both flag
`components-range-slider--default` and `components-stepper-horizontal-stepper--default`
as light-theme axe failures; run 1 does not. Every other light-theme story agrees across
all three runs. This is two additional stories, not a rounding artifact, and it is not
the `dda-header` story — it is a **separate, previously-undocumented flake on the light
side.** Tasks 3 and 4 both reported 16 light instances/stories; this task's designated
run alone reported 14. Across five total measurement sessions now (Task 3, Task 4, and
this task's three runs — treating runs 2/3 as one data point since they agree with each
other), light has read 16 four times and 14 once.

**Dark-theme finding, already documented, reconfirmed:** the only difference between run
1 and runs 2/3 on the dark side is `Components/Header Default`: 1 violation
(`color-contrast`) in run 1, 2 violations (`color-contrast` + `link-name`) in runs 2/3.
Same as Task 3's original report, Task 3's fix round, and Task 4's rerun — this story has
now read 0/1/2 violations across at least six independent measurement sessions.

**Conclusion: the sweep is not yet reproducible run-to-run in either theme.** The union
figure (29 distinct stories) and the dark distinct-story count (25) happen to be stable
across every run recorded so far, in every task — but the instance counts, and the exact
identity of which stories fail in light theme, are not. Task 9, when turning this sweep
into a CI gate, should not expect a single run's count to match exactly on the next run;
it should decide in advance how much variance the gate tolerates, rather than treating
any one number here as the permanent target.

### WCAG 2.4.7 split — do not merge these two rows

**13 confirmed failures** (`dda-button`, `dda-creditcard-field`, `dda-dropdown`,
`dda-input`, `dda-link-button`, `dda-search-input`, `dda-select`, `dda-textarea`) are
cases where Tab-focusing the element produces *no visible change at all* — no outline,
box-shadow, or colour change anywhere in the ancestor chain (verified against an
unfocused-state baseline captured before any Tab press). These are real WCAG 2.4.7
defects.

**15 needs-manual-contrast-check** entries (`dda-button`, `dda-link-button`,
`dda-footer`, `dda-home-banner`, `dda-number-field`, `dda-phonefield`,
`dda-search-input`) are cases where focus *does* change something (typically a
background-color, border-color, or text-color) but no `outline` or `box-shadow` appears
anywhere in the ancestor chain. WCAG 2.4.7 permits a focus indicator through means other
than outline/box-shadow, provided the change carries sufficient contrast against the
unfocused state — a judgment this tool cannot make (it stopped at "cannot find outline
or box-shadow," not "cannot find a discernible change"). These 15 are not confirmed
defects; treat each as needing a human contrast check before deciding whether it's a
fault. Full list, from this task's `console.warn` capture: `components-button--
default-primary/error-primary/surface-primary/icon-button`, `components-link-button--
default-primary/error-primary/surface-primary/icon-button`, `components-footer--default`,
`components-home-banner--default/autoplay`, `components-number-field--disabled/error`,
`components-phone-field--error`, `components-search-input--with-button`.

### Ghost attribute marked informational, not a real defect

`dda-breadcrumb`'s `breadcrumbs` finding (1 of the 106, in `dda-breadcrumb.stories.tsx`)
is a known-benign false-positive-by-design: the story destructures `breadcrumbs` out of
`args` and re-encodes it into a real `data-breadcrumbs` attribute
(`const { breadcrumbs, ...otherArgs } = args;`). The rendered markup works correctly.
It is reported because the checker's contract is "an `argTypes`/`args` key that is not a
declared prop is a finding," and detecting "this key gets destructured out and
re-encoded under a different, real attribute name" needs semantic analysis beyond what
the tool does. **Marked informational, not removed from the count** — the total above is
still 106.

### Coverage gap: 2 of 34 components have no Storybook stories

`dda-banner` and `dda-ui-card` have no `.stories.tsx` file. They were linted and
API-checked (both show 0 ghost attributes), but the axe sweep, WCAG 2.5.8, and WCAG 2.1.1
checks only run against stories — these two components were never exercised by any of
those three tools. Their `0` cells below mean "not measured," not "measured and clean."

## Also recorded: findings the counters above don't cover

Carried forward from Tasks 1-4 for Task 7/9, confirmed still present on this branch as of
this run:

- **`dda-footer` and `dda-sticky-footer` render with an open shadow root**, against
  CLAUDE.md's stated `shadow: false` + global-CSS convention. Confirmed by Task 4's
  direct DOM instrumentation (naive `document.activeElement` only ever resolved to the
  `<dda-footer>` host, not the real focused descendant, until the check was rewritten to
  drill through `shadowRoot.activeElement`).
- **`dda-tabs.tsx:59` applies the same `id` to every generated tab button** — a
  duplicate-ID bug surfaced as a side effect of Task 4's keyboard-reach identity fix
  (`components-tabs--text-tabs` was undercounted 2/3 reachable until the check stopped
  conflating siblings that shared this `id`).
- **`dda-number-field`'s "Disabled" story never actually disables its input** —
  `dda-number-field` has no `disabled` `@Prop()` at all, so the story's disabled-looking
  state is styling only, not a real `disabled` attribute on the `<input>`.
- **`packages/angular/projects/stencil-wrapper/package.json`** was invalid JSON (trailing
  comma) from the initial commit until fixed on this branch. Confirmed valid now
  (`node -e "JSON.parse(...)"` succeeds).
- **`package-lock.json`** declared only the Windows native binary for `@swc/core`, so no
  Linux machine could build Storybook, until fixed on this branch. Confirmed now: the
  lock declares all 10 `@swc/core-*` platform packages (darwin-arm64, darwin-x64,
  linux-arm64-gnu, linux-arm64-musl, linux-arm-gnueabihf, linux-x64-gnu, linux-x64-musl,
  win32-arm64-msvc, win32-ia32-msvc, win32-x64-msvc).
- **`@stencil/core` version drift** — the lock file pinned 4.24.0 while the working tree
  had drifted to 4.43.5, so `npm ci` produced a different build from what developers
  test. Now pinned exactly: `packages/stencil/package.json` and `package-lock.json` both
  declare `4.43.5`. Confirmed by this task's own `npx stencil build` output
  (`v4.43.5`).
- **ESLint's `files: ['src/**/*.tsx']` scope excludes `.js` files.**
  `src/utils/applyTheme.js` is outside that glob, so its `no-undef: off` override (added
  for `.tsx` files, where Stencil's JSX globals would otherwise false-positive) never
  reaches it, and the file escapes linting entirely except for whatever the base config
  still applies. This is why its 1 `no-undef` error (on `document`) shows up in the
  Totals table but has no home in the per-component table — it isn't a component file.
